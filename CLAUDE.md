# Programming Lessons C++ — project instructions

A C++17 course for Bulgarian olympiad preparation (NOI Groups C and D), written
for **5th–6th graders**. The end product is a static site: a hub that lists
lessons, one page per lesson, and a searchable catalogue of 768 classified
competition problems.

Everything is plain HTML/CSS/JS generated by Python. No build system, no
dependencies beyond `python-docx` (only for the optional `.docx` export).

---

## 1. Problem classification — always start here

**`Group C and D problems/index.html` is the single source of truth for problems.**
Never invent a problem, a URL, a difficulty or a tag. Never fetch the Arena
site to look one up. Query the catalogue.

It holds 768 problems (Groups C and D, NOI municipal/regional/national rounds
and the four seasonal tournaments, 2007–2026), embedded as `const DATA = {...}`.
Each row carries:

| field | meaning |
|---|---|
| `name` | problem short name, as it appears on the Arena |
| `comp` | competition (`NOI - Municipal round`, `Autumn tournament`, …) |
| `group` | `C` or `D` |
| `year` | 2007–2026 |
| `diff` | 1 very easy · 2 easy · 3 medium · 4 hard · 5 very hard |
| `alg` / `alg2` | primary and optional secondary algorithm (27-term vocabulary) |
| `techs` | technique tags (34-term vocabulary) |
| `hint` | one-line description of the intended solution |
| `url` / `pdf` | Arena problem page and Bulgarian statement PDF |

### Querying it

```bash
python tools/catalog.py vocab
```

```bash
python tools/catalog.py stats --alg "Prefix sums" --group D
```

```bash
python tools/catalog.py find --any-tech Stacks --any-tech Queues --diff 2-3 --limit 20
```

```bash
python tools/catalog.py pick --alg "Greedy" --diff 2-3 --limit 6 --section A --out 22_Greedy/problems.json
```

Filters: `--alg`, `--any-alg` (OR), `--exclude-alg`, `--tech` (AND, repeatable),
`--any-tech` (OR), `--group`, `--diff 2-4`, `--year 2015-2026`, `--comp`, `--q`,
`--not-used`. All matching is case-insensitive substring matching, so `--tech Arrays`
also matches `2D arrays`; use `--tech "Counting array"` when you need precision.

`--not-used` hides problems already placed in some lesson's `problems.json`, which
is how you avoid assigning the same problem twice. `find` marks reused problems
with `[in <lesson>]`.

If a row looks miscategorised, fix it in `Group C and D problems/index.html` —
do not work around it in a lesson.

`03_Strings` is the reference lesson. Match its shape.

## 3. Building

```bash
python tools/render_lesson.py 03_Strings
```

`--html-only` skips the DOCX (useful when `python-docx` is missing).

```bash
python tools/build_site.py
```

Rebuild the hub after adding a lesson, changing `syllabus.json`, or assigning
problems — it reads the filesystem to decide which lessons are written and how
many problems each one has. It warns about lessons whose catalogue pool is thin.

Generated files (`index.html`, `SYLLABUS.md`, `NN_Topic/*.html`, `NN_Topic/*.docx`)
are outputs. Edit `syllabus.json`, `content.py` and `problems.json` instead.

## 4. Writing a lesson

1. Add or confirm the entry in `syllabus.json` (slug, title, summary, `covers`,
   catalogue `filters`).
2. `mkdir NN_Topic`.
3. Write `NN_Topic/content.py`. Copy the structure of
   [03_Strings/content.py](03_Strings/content.py):

   ```python
   SLUG, BRAND, FOOTER, TITLE, SUBTITLE
   PITFALLS_TITLE          # optional; defaults to "<n> pitfalls that cost real marks"
   LEGACY_DONE_KEY         # optional; only 03_Strings needs it
   SECTIONS    = [ (id, "1. Title", [blocks]), ... ] # theory
   CHEATSHEET  = [ (what, how), ... ]
   PITFALLS    = [ (title, explanation), ... ]
   COMPLEXITY  = [ (operation, cost), ... ]
   ```

   Block kinds inside a section: `("p", text)`, `("code", text)`,
   `("note", text)`, `("table", [headers], [[row], ...])`, `("h3", text)`,
   `("list", [items])`. Inline markup in any text: `` `code` `` and `**bold**`.

   The four trailing chapters (cheat sheet, pitfalls, complexity, practice) are
   numbered automatically from `len(SECTIONS)` — do not hardcode their numbers.
   There is no "How to use this lesson" section; the page opens straight on
   section 1.

4. Build `NN_Topic/problems.json` with `tools/catalog.py pick`, then group the
   problems into lettered sections:

   ```json
   {"group": "D",
    "groups": [{"key": "A", "name": "A. ...", "maps": "Theory: sections 2 and 7"}],
    "problems": [{"section": "A", "pid": 208, "title": "word", "en": "Even word",
                  "tech": "char->index, ASCII arithmetic", "family": "Municipal round",
                  "year": 2009, "diff": 1,
                  "url": "https://arena.olimpiici.com/#/catalog/92/problem/100208"}]}
   ```

   `maps` must point back at the theory sections that solve that group. The
   selection rules are in section 6.

5. `python tools/render_lesson.py NN_Topic && python tools/build_site.py`.

## 5. Content conventions

- **Write for 5th–6th graders.** Assume only what earlier lessons taught. Short
  sentences, everyday words, one idea per paragraph, and a small worked example
  for every rule. Explain *why* a thing is done, not only what to type.
- **Only the basics.** Teach the few ideas a Group D problem in this lesson
  needs, and stop. Leave out rare functions, corner-case trivia, performance
  folklore and "good to know" asides. A lesson is about 5–7 short theory
  sections, a cheat sheet of about 10 rows, 4–6 pitfalls and a complexity table
  of about 5 rows. If a section needs more than two or three code blocks, it is
  doing too much.
- **No "How to use this lesson" section.** Do not add `HOWTO` to `content.py`.
- **Keep the C++ small.** No lambdas, no iterators as a concept (`s.begin(), s.end()`
  is a fixed phrase meaning "the whole string"), no templates, no `auto` tricks, no
  structured bindings, no `<sstream>`, no `string_view`, no `<charconv>`, no
  `reserve`/`resize`. Index with `int` and write `int n = s.size();` before the loop.
  A tool earns its place only when a problem in the lesson needs it; anything
  heavier (KMP, hashing, tries) belongs in a later lesson.
- **C++17.** No C++20 features (`<ranges>`, `<span>`, concepts, `starts_with`,
  `ends_with`, `contains`) — say so where a pupil would expect them to exist.
- **Contest style, not production style.** `using namespace std;`, short names,
  global arrays. Say when a habit is contest-only and would be wrong elsewhere.
- **Every snippet compiles** as written, or sits inside a stated context.
- **British English**, sentence case in headings, an en dash for ranges.
- Complexity is stated for every operation introduced.
- Pitfalls are concrete failures that cost marks, not style advice.
- Problem statements on the Arena are **in Bulgarian**; the `hint` field and the
  `en` field carry the English gloss. Keep lesson prose in English.

## 6. Problem selection

- **Exactly 12 problems per lesson, all from Group D.** Never Group C. The
  `group` field of `problems.json` is `"D"`.
- **Group them by the lesson's subtopics**: 3–4 lettered groups, each one the
  practice for one subtopic (one or two theory sections). Usually 4 groups of 3,
  or 3 groups of 4.
- **Complexity goes up.** Inside every group the problems run easiest first and
  the difficulty never drops; the groups follow the order of the theory, so
  the page as a whole climbs. Start at difficulty 1–2 where the topic has such
  problems and finish at 3–4. A 5 is too hard for this audience.
- Every group maps to a theory section. If a group has no section, either write
  the section or drop the group.
- When the catalogue tag for a topic is thin in Group D (heaps, stacks, pairs),
  select on shape: problems a pupil would naturally solve with the lesson's
  tool, even if the catalogue tags them otherwise. Say how the tool is used in
  the problem's `tech` line.
- Do not spend a later lesson's flagship problems. Prefix sums, counting arrays,
  2D grids, sorting and two pointers each have their own lesson; an array
  lesson uses problems where the array itself is the difficulty.
- Check `--not-used` before assigning. A problem may appear in two lessons only
  if it genuinely teaches both techniques.

## 7. Design

The lesson pages and the hub are theme-aware: a light palette on bare `:root`,
overridden under `@media (prefers-color-scheme: dark)` guarded by
`:root:not([data-theme="light"])`, and again under `:root[data-theme="dark"]` so
the toggle wins. The theme choice is shared site-wide in `localStorage` under
`cpp_lessons_theme`; per-lesson progress lives under `cpp_done_<SLUG>`. Every
storage access is wrapped in try/catch — these pages are opened over `file://`.

Lesson CSS/JS live in `tools/render_lesson.py`; hub CSS/JS in
`tools/build_site.py`. Change them there, then rebuild every lesson.
